# AIKB Agent 规则

本规则只适用于已由 `ENTRY_RULES.md` 判定需要接入 AIKB 的任务。Markdown 是知识事实源，SQLite/MCP 是可重建的发现与读取能力；当前项目代码、配置、测试和适用版本始终是当前事实的首要证据。

## 1. 优先级与首次接入

规则冲突时依次遵循：系统、开发者和平台约束；用户当前任务要求；当前项目约定与证据；`USER_RULES.md`；已验证的 AIKB 知识；通用经验。事实不一致时先核对版本和当前证据，过期知识作为修订候选，不自动改写个人规则。

首次接入不默认读取 `INDEX.md`、`CATALOG.md`、内容目录或根目录人类手册 `README.md`。仅按任务需要通过下节路由加载最少知识，并向用户简要说明接入及实际加载的主题。

## 2. 知识检索

按以下顺序选择，避免无效搜索：

1. 当前上下文已有且仍可信：直接使用。
2. 已知准确文件或稳定 ID：直接读取 Markdown 或调用 `read_knowledge`。
3. 不知道位置：调用 `search_knowledge`，默认少量结果、每文档一个片段，再读取选中的知识。
4. MCP 不可用、索引陈旧或调用失败：按 `INDEX.md → 分类 README → 主题 README → 具体文件` 降级。
5. 仅在全库治理或正式写入前查重时读取 `CATALOG.md`。

检索算法由服务内部选择，Agent 不指定 FTS、短词回退或未来向量实现。搜索结果只定位候选，正式采用前核对 Markdown、版本和 `content_hash`；关系默认不展开，必要时只扩展一层少量关联。没有相关知识时明确说明，不把模型自身知识表述为 AIKB 结论。

## 3. 本机工作状态

`workspace/` 是不进 Git、不跨机器的未完成任务运行面，不是聊天记忆库。只有任务已形成实际进度、决定、修改、验证、阻塞或交接时才创建工作项；普通问答、讨论和无状态变化的轮次不写检查点。

- 同一任务只用一个 `work_id`，通过 `agent`、`session_id`、`role` 区分来源。
- 恢复时先匹配项目；唯一候选加载紧凑胶囊，多个候选只列摘要。继续实施前复核 Git 分支、revision 和工作区。
- 在关键决定、实质修改及验证、阻塞、Agent 交接、上下文压缩前、未完成会话结束前和关闭任务时写检查点；无变化不写。
- 只保存恢复所需摘要，不保存完整聊天、隐藏推理、密钥、原始日志、完整 diff 或不必要的敏感信息。
- 任务完成、放弃或被替代时关闭并归档；SQLite 损坏时从工作 Markdown 重建。

工作状态中的候选结论不能自动进入正式知识。用户要求跳过 AIKB 时也不读写工作状态，除非同时明确要求继续已保存任务。

## 4. 候选知识与正式写入

工程任务中主动识别能减少未来调查成本或错误概率的长期知识，但不在每次任务后自动写库。准备正式新增、修订、归档或淘汰知识时，先读取并遵循 `system/rules/CONTRIBUTING.md`，完成查重、验证、归类、索引更新和检查。

满足贡献规则的常规写入无需逐次请求确认；涉及敏感信息、争议结论或需要替用户作出新的长期决策时必须先确认。证据、范围或归类不足时进入 Inbox。MCP 当前不提供正式知识写入工具，正式写入通过文件修改完成。

## 5. 复用与边界

同一会话按 `id + content_hash` 复用已加载规则和知识。只在用户要求刷新、上下文丢失、项目或领域变化、文件变化或准确性无法确认时最小化补读，不全库重载；上下文压缩后优先使用紧凑工作状态恢复。

`system/` 保存控制面，`content/` 保存候选和正式知识，`workspace/` 保存本机状态与派生数据库，根目录保存稳定入口和索引。控制面不进入 `CATALOG.md`，工作状态不进入知识索引，正式知识只写入 `content/`。
