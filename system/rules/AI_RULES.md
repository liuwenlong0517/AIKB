# AIKB Agent 规则

本规则适用于已由 `ENTRY_RULES.md` 判定需要接入 AIKB 的工程任务。AIKB 是独立于具体 Agent 的长期工程知识层；Markdown 是知识事实源，SQLite/MCP 只是可重建的发现与读取能力，当前项目代码、配置、测试和适用版本的权威文档仍是当前事实的首要证据。

## 1. 优先级

规则冲突时按以下顺序处理：

1. 系统、开发者、平台安全策略和运行环境强制指令。
2. 用户对当前任务的明确目标、限制和临时要求。
3. 当前项目代码、配置、测试和项目约定。
4. `system/rules/USER_RULES.md` 中的长期个人偏好。
5. 已验证的项目知识。
6. 通用知识、经验和默认工作流。

事实冲突时优先采用当前可验证证据；先检查版本和适用范围，再把确认过期的 AIKB 内容作为修订候选。当前任务的临时要求不得自动改写个人规则。

## 2. 首次接入与最小上下文

是否接入及何时延迟接入只由 `ENTRY_RULES.md` 决定。首次接入时：

1. 仅在尚未加载、文件已变化或内容无法确认时读取 `system/rules/USER_RULES.md`。
2. 读取 `INDEX.md` 建立轻量拓扑；不默认读取 `CATALOG.md` 或扫描内容目录。
3. 只有当前任务需要具体知识时才按下节路由发现并读取最少内容。
4. 向用户简要反馈接入及实际加载的主题。

根目录 `README.md` 是面向人类维护者的完整手册，不属于首次接入、知识检索、工作状态恢复或常规知识写入的默认上下文。只有用户明确要求阅读，或任务本身是在维护 AIKB 控制面、安装流程或文档时才按需读取；不得仅为了解项目概况自动加载。

同一会话复用已加载规则和知识，不按轮次重复读取。已加载知识以 `id + content_hash` 识别；版本未变化时不重复检索或读取。

## 3. 知识检索路由

严格按以下顺序选择，不把每个问题都交给搜索：

1. 当前上下文已有且仍可信的内容：直接使用。
2. 已知准确文件或稳定知识 ID：直接读取目标 Markdown 或调用 `read_knowledge`，不先搜索。
3. 不知道知识位置：调用 `search_knowledge` 做发现式检索；默认少量结果、每文档一个片段。
4. MCP 不可用、索引陈旧或调用失败：按 `INDEX.md → 分类 README → 主题 README → 具体文件` 降级。
5. 仅在全库浏览、知识治理或正式写入前查重时读取 `CATALOG.md`。

Agent 不判断 FTS、短词回退或未来向量实现，检索算法由服务内部选择。搜索结果只负责定位候选；正式使用时以当前 Markdown、适用版本和 hash 为准。默认不展开关系；确需调用背景时最多扩展一层少量关联。没有相关知识时应明确说明，不得把模型自身知识说成 AIKB 既有结论。

## 4. 本机工作状态

`workspace/` 是不进 Git、不跨机器同步的运行面，服务于未完成工程任务的会话继承，不是聊天记忆库。只有形成了实际工程状态、关键决定、阻塞、交接或完成结果时才创建或更新工作项；普通问答、尚未形成任务的讨论和每轮对话不写检查点。

- 同一任务只有一个 `work_id`。Codex、Claude Code 或未来 Agent 通过开放的 `agent`、`session_id`、`role` 字段区分来源，在同一工作项中追加检查点，不拆成多份任务真相。
- 恢复任务时先匹配当前项目；唯一候选只加载紧凑恢复胶囊，多个候选只列摘要，不自动合并。
- 继续实施前必须复核当前 Git 分支、revision 和工作区状态；检查点记录不是当前代码的替代证据。
- 在关键决定、实质修改及验证、阻塞、Agent 交接、上下文压缩前、未完成会话结束前和任务关闭时写检查点；没有状态变化时不写。
- 检查点只允许写入 `workspace/`。不得保存完整聊天、隐藏推理、密钥、原始日志、完整 diff 或不必要的敏感信息。
- 工作状态中的候选知识不能自动进入 `content/`；必须另行执行正式知识准入和验证流程。
- 用户明确要求跳过 AIKB 时默认不读取或写入工作状态；用户同时明确要求继续已保存任务时除外。

任务完成、放弃或被替代时调用关闭能力移入本机归档。SQLite 工作索引损坏时从工作 Markdown 重建。

## 5. 主动发现与正式写入

开发、调试、评审、发布和技术决策中，应识别可能减少未来调查成本或错误概率的长期知识，但不要在每次任务后自动写库。正式写入前：

1. 读取或复用 `system/rules/CONTRIBUTING.md`。
2. 用 MCP、局部 README、关键词和 `CATALOG.md` 查重。
3. 用当前代码、测试、运行结果、配置、适用版本的权威文档或用户确认验证。
4. 选择正确目录和模板，使用稳定 `id`、受控 `type` 和显式 `relations`。
5. 更新最近一级 README 和 `CATALOG.md`；只有全局入口变化时更新 `INDEX.md`。
6. 报告写入位置、验证依据和适用边界。

证据、适用范围或归类不足时使用 Inbox；敏感信息、争议结论或需要用户作出新的长期决策时先请求确认。第一阶段 MCP 不提供正式知识写入工具，正式知识仍通过文件修改和贡献流程完成。

## 6. 重载与边界

只在用户要求刷新、新会话或上下文丢失、项目切换、文件变化、新领域出现或准确性无法确认时最小化重载。上下文压缩后的恢复优先使用紧凑工作状态，再补读确实缺失的规则或知识，不全库扫描。

目录职责：

- `system/`：规则、Schema、MCP 实现、Agent 适配器和测试。
- `content/`：经过治理的正式知识和候选知识。
- `workspace/`：本机工作状态和可重建数据库；除说明与忽略规则外不进 Git。
- 根目录：稳定入口、轻量索引、完整目录、项目说明和仓库配置。

控制面文件不登记到 `CATALOG.md`，工作状态不进入知识索引，正式知识不得写入 `system/` 或 `workspace/`。任何工具都必须限制路径范围、参数化 SQL，并在异常时保留 Markdown 与上一份可用数据库。
