# AIKB Agent 规则

本规则适用于 `ENTRY_RULES.md` 判定需要接入 AIKB 的任务。Markdown 是知识事实源；SQLite/MCP 是可重建的发现与读取层；当前项目代码、配置、测试和适用版本优先。

## 1. 优先级与首次接入

规则冲突时依次遵循：系统、开发者和平台约束；用户当前任务的明确范围；项目约定与证据；`USER_RULES.md`；已验证的 AIKB 知识；通用经验。用户当前任务不能默示豁免删除、覆盖、外发、密钥、高风险写入或长期决策的确认要求；事实不一致时先核对版本和当前证据，过期知识只作为修订候选，不自动改写个人规则。

首次接入不默认读取控制仓或知识仓的 `INDEX.md`、知识仓 `CATALOG.md`、内容目录或控制仓人类手册 `README.md`；按下节路由加载最少知识，并简要报告实际主题。

## 2. 知识检索

按以下顺序选择：当前上下文；已知准确文件或稳定 ID；`search_knowledge` 定位少量候选；`read_knowledge` 核对选中文档。MCP 不可用、索引陈旧或调用失败时，从控制仓 `INDEX.md` 转入知识仓 `INDEX.md → 分类 README → 主题 README → 具体文件`。仅全库治理或正式写入前查重才读知识仓 `CATALOG.md`。

检索算法由服务选择，Agent 不指定 FTS、短词回退或未来向量实现。搜索结果只定位候选；正式采用前核对 Markdown、版本和 `content_hash`。关系默认不展开，必要时只扩展一层少量关联。没有相关知识时明确说明，不把模型知识说成 AIKB 结论。

## 3. 本机工作状态

`workspace/` 是不进 Git、不跨机器的未完成任务运行面，不是聊天记忆库。只有任务形成实际进度、决定、修改、验证、阻塞或交接价值时才创建工作项。

- 同一任务只用一个 `work_id`；任务固定记录 owner，检查点另记录 author，通过 `agent`、`session_id`、`role` 区分来源，最近 author 不得被当作 owner。
- 恢复时先匹配项目，再过滤当前 owner 或已登记 participant；只有授权范围内的唯一候选加载紧凑胶囊，多个候选只列摘要。继续实施前复核 Git 分支、revision 和工作区。
- 在关键决定、实质修改及验证、阻塞、交接、上下文压缩、未完成会话结束和关闭任务时写检查点；无变化不重复写。
- 只保存恢复摘要，不保存完整聊天、隐藏推理、密钥、原始日志、完整 diff 或不必要敏感信息。
- 任务完成、放弃或被替代时关闭并归档；SQLite 损坏时从工作 Markdown 重建。

工作状态中的候选结论不能自动进入正式知识。用户要求跳过 AIKB 时也不读写工作状态，除非同时明确要求继续已保存任务。

## 4. 候选知识与正式写入

主动识别能减少未来调查成本或错误概率的长期知识；不在每次任务后自动写库。准备正式新增、修订、归档或淘汰知识时，先读取并遵循 `system/rules/CONTRIBUTING.md`，完成查重、验证、归类、索引更新和检查。

低风险且证据完整的 `factual-update` 或 `operational-solution` 可按项目授权自动处理；`decision-proposal`、supersession、分类迁移、敏感变化和新的长期决策必须先确认或独立审查。证据、范围或归类不足时进入 Inbox。MCP 当前不提供正式知识写入工具，正式写入通过文件修改完成。

## 5. 复用与边界

同一会话按 `id + content_hash` 复用规则和知识；仅在用户要求刷新、上下文丢失、项目或领域变化、文件变化或准确性无法确认时最小化补读。上下文压缩后优先使用紧凑工作状态恢复。

`AIKB_HOME` 控制仓保存入口和 `system/`；`AIKB_KNOWLEDGE_HOME` 知识仓保存正式知识、候选、索引和目录；`workspace/` 保存本机状态与派生数据库。控制面不进知识仓 `CATALOG.md`，工作状态不进知识索引，正式知识只写知识仓。拆仓后两仓分别提交，知识变更不得修改控制仓转发入口。

`workspace/audit/` 是独立本机审计面。默认 `safe` 记录 MCP/hook 的时间、Agent、会话标签、摘要、结果和耗时；显式 `AIKB_AUDIT_CAPTURE_LEVEL=diagnostic|full-local` 时才保存脱敏、限长的输入输出。任何级别均不得记录聊天全文、隐藏推理、transcript、二进制、未脱敏密钥或完整 traceback。JSONL 是事实源，Excel 是主视图，Markdown 报告暂时弃用；审计必须 fail-open，不进知识仓且不自动清理。

## 6. 工作项归属与跨 Agent 协作

项目路径相同、项目下只有一个活动任务，均不等于当前会话拥有该任务。工作项必须区分不可由普通检查点覆盖的 `owner_agent`、`owner_session_id`，以及每次检查点的 `author_agent`、`author_session_id` 和 `role`；最近作者不得被解释为所有者。

SessionStart 自动恢复、Stop hook 阻断、检查点写入和任务关闭，只能作用于当前 owner 或已登记的 participant。发现项目有其他会话的活动任务时，不注入任务正文、不阻断当前会话、不自动写入或关闭；只记录外来任务摘要和 `foreign_active_work` 审计结果。跨 Agent 续写必须有用户明确要求、owner 显式交接或预先登记的参与关系；同仓库、同项目或唯一候选不能代替授权。

所有权和参与关系通过控制面登记，不能由调用者仅凭请求参数自称：MCP 服务启动时的 `--agent` 必须与请求中的 Agent 身份一致；`session_id` 必须原样使用当前 Hook 观测到的值，用于防止误把其他会话的任务归入当前会话，但不是密码学凭据。不得把 Agent-only 匹配伪装成 `session-bound`。同一 Windows 用户下能够直接修改工作区或伪造调用的恶意进程不在本规则的信任边界内；需要强身份认证时，另行使用 OS ACL、可信 broker 或其他进程级隔离。交接应绑定任务 ID、接收会话、授权范围和时间，并可撤销。旧任务无法确定 owner 时标记为 `legacy-unbound`，在重新认领前不得自动恢复或阻断。

## 7. 明确授权与不可豁免操作

用户当前任务只授权其中清楚写明的目标和范围；模糊措辞不能推导出删除、覆盖、外发、密钥处理、改变安全边界或替用户作长期决策的许可。删除、覆盖、外发、密钥、正式知识晋升、规则修改和任务归属变更等不可逆或高风险操作，不因“当前任务要求”自动豁免，除非用户对本次具体操作明确授权。系统、开发者和平台约束用于表达必须遵循的上级限制，不能被 Agent 用来扩大用户授权范围。

## 8. 知识变更的客观处置

正式知识变更先声明固定的 `change_class`：`factual-update`、`operational-solution`、`decision-record`、`decision-proposal`、`supersession`、`taxonomy-change` 或 `sensitive-change`。新长期取舍使用 `decision-proposal`，只能进入 candidate；没有用户确认、既有决策记录或其他权威来源，不得自行标记为 verified。替代仍在使用的正式条目、分类迁移和敏感变更必须先审批；不能用“常规”“无争议”或“已验证”自行绕过确认门。

正式条目声明 `authority` 和结构化 `evidence`。证据至少包含可复核的命令、测试名、提交号、逻辑文件、运行观察、适用版本的权威 URL 或用户确认引用；自由文本和模型记忆不是证据。validator 只能检查字段、格式、范围、路径/提交可解析性和证据留痕，不能证明命令确实执行过、URL 一定支持结论或自然语言结论必然正确；无法复核时保持 candidate。

每次任务收尾都要报告知识处置：`none`、`candidate-created`、`formal-updated` 或 `deferred` 及原因。命中重复调查、跨多个模块、反直觉约束、高成本故障、规则未覆盖问题或用户确认的长期决策之一时，必须进行该处置，不得以“无长期价值”无说明跳过。候选需有 owner、captured_at、next_action_due 和 review_state；到期、重复和无 owner 的 Inbox 由 review 流程处理。
