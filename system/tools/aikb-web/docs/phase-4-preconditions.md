# AIKB WebUI 阶段 4 规则治理前置契约与开发计划

本文档冻结阶段 4 的任务分发条件。2026-08-30 已完成波次 0 的共享基础和波次 1 的规则读取/候选预览；当前只开放四项规则审阅及 `USER_RULES.md` 完整差异预览，不开放应用写入、安装、修复、索引重建或 Git 写操作。阶段 4 拆为 4A“规则治理”和 4B“安装与修复”；只有 4A 经真实 Windows 回归并形成稳定事务模型后，才为 4B 单独制定动作准入契约。

## 1. 阶段结论与首批边界

阶段 3 已提供静态动作注册、预览令牌、任务 JSONL、SSE、Windows Job Object 和审计 v3，可作为有副作用操作的控制骨架，但不能直接把规则正文作为普通任务参数保存。阶段 4A 第一小版本只实现：

- 用稳定规则 ID 浏览 `ENTRY_RULES.md`、`system/rules/USER_RULES.md`、`system/rules/AI_RULES.md` 和 `system/rules/CONTRIBUTING.md`；
- 只允许修改 `system/rules/USER_RULES.md`，其他三项保持只读；
- 提供完整差异预览、候选校验、仓库冲突检查、高风险确认、原子替换、失败恢复和审计关联；
- 应用操作进入现有任务中心，但任务参数和事件只保存 `change_id` 与安全摘要，不保存规则正文或完整 diff；
- 继续只监听本机回环地址，不增加登录、多用户或远程访问模式；
- macOS 继续只保留公共接口位置，不实现或声称支持。

以下能力不进入 4A 第一小版本：

- 修改 `ENTRY_RULES.md`、`AI_RULES.md`、`CONTRIBUTING.md`、`INDEX.md`、知识仓、Agent 根指令或适配器配置；
- 任意文件路径、批量替换、上传文件、富文本/HTML 编辑和脚本生成；
- 自动 `git add`、commit、push、reset、checkout、stash 或分支切换；
- 安装、卸载、修复、清理、索引重建和审计报告生成；
- 直接注册 `setup-aikb.ps1`、`install-all.ps1` 或 `doctor.ps1`。这些脚本包含多个副作用和 probe，必须在 4B 拆成可预览、可回滚的专用动作后再准入。

## 2. 静态规则注册表

后端使用受版本控制的 Python 静态注册表，浏览器只能提交规则 ID，不能提交或覆盖物理路径。首批注册表固定为：

| rule_id | 逻辑目标 | 可读 | 可写 | 风险 | 说明 |
|---|---|---:|---:|---|---|
| `entry` | `ENTRY_RULES.md` | 是 | 否 | 高 | Agent 接入引导，只提供审阅 |
| `user` | `system/rules/USER_RULES.md` | 是 | 是 | 高 | 第一小版本唯一可修改规则 |
| `agent` | `system/rules/AI_RULES.md` | 是 | 否 | 高 | AIKB 工作协议，只提供审阅 |
| `contributing` | `system/rules/CONTRIBUTING.md` | 是 | 否 | 高 | 正式知识贡献规范，只提供审阅 |

注册表对外只返回 ID、标题、说明、字符预算、可读/可写状态、当前内容哈希和最近 Git revision。物理路径、磁盘根目录和任意路径拼接不能进入 API。新增可写规则必须修改静态注册表、专用验证器、审计投影、文档与真实回归，不能由配置文件或浏览器动态开启。

规则内容统一按 UTF-8 无 BOM 和 LF 规范化。拒绝 NUL、U+FFFD、无法解码字节、单行超过 4 KiB、总内容超过注册表预算或 64 KiB 的请求。首批仍以现有 `validate-structure.ps1` 中更严格的具体规则预算为准。

## 3. REST 与页面契约

阶段 4A 新增以下资源：

- `GET /api/v1/rules`：规则目录和能力；
- `GET /api/v1/rules/{rule_id}`：当前正文、安全元数据、`content_hash` 和短 Git revision；
- `POST /api/v1/rules/{rule_id}/preview`：提交 `base_content_hash` 与候选正文，返回候选校验结果、完整统一 diff、`change_id`、`preview_digest` 和五分钟单次确认令牌；
- `POST /api/v1/rules/{rule_id}/apply`：只接收 `change_id`、`preview_digest` 和确认令牌，创建受控任务并返回任务 ID；
- `GET /api/v1/rule-changes/{change_id}`：返回安全状态、哈希、校验摘要和关联任务，不返回候选正文、备份或物理路径。

所有 POST 继续要求 `application/json`、`X-AIKB-Request: 1`、严格 Host/Origin 和无通配 CORS。请求体、错误、访问日志、任务事件和审计均不得记录规则正文、完整 diff 或确认令牌。

前端采用“规则目录 / 正文审阅或编辑 / 差异和校验”三栏布局。首批使用受控纯文本编辑器，不新增 Monaco 依赖；如果后续引入 Monaco，规则路由和编辑器必须懒加载，避免继续扩大当前主包。只读规则不显示保存入口；可写规则必须明确显示“修改只影响新会话，已运行 Agent 不会自动重载”。

差异必须完整展示后才能确认。候选最多 2,000 行，统一 diff 最多 4,000 行或 256 KiB；超过预算直接拒绝预览，不能截断后仍允许应用。关闭页面、刷新页面或令牌过期不会自动写入。

## 4. 预览、确认与仓库并发

预览生成前必须同时检查：

1. 控制仓处于普通分支状态，不在 merge、rebase、cherry-pick、bisect 或未合并冲突中；
2. 控制仓工作树和暂存区全仓干净；
3. `base_content_hash` 与当前目标内容一致；
4. 目标仍位于静态注册表且当前版本允许写入；
5. 候选通过编码、预算、职责词、禁止词和可移植性检查。

第一小版本采取“全仓干净才允许预览和应用”的保守策略，不仅检查目标文件。这样可以避免结构校验受其他未提交修改影响，也避免 Web 写入与开发中的变更混成一次后续提交。未来若放宽为目标文件级冲突检测，必须另行评审并扩展并发回归。

确认令牌必须绑定：

- `rule_id`、`change_id` 和风险级别；
- 预览时的控制仓完整 revision；
- 原内容哈希、候选内容哈希和完整 diff 哈希；
- 校验器版本、`preview_digest` 和过期时间。

令牌五分钟有效、只能成功消费一次、服务重启后失效。应用前重新读取仓库状态、revision 和内容哈希；任一字段变化均返回冲突，不能自动重新预览、合并或覆盖。失败绑定不得消耗仍可用于正确请求的令牌；真正开始应用时才原子消费。

## 5. 变更事实源、原子写入与恢复

规则变更使用专用事务目录，不把正文塞入通用任务事实源：

```text
workspace/runtime/web/rule-changes/<YYYY>/<MM>/<change_id>/
├─ transaction.json    # 逻辑 ID、哈希、状态、时间和任务关联
├─ candidate.md        # 待应用候选；短期本机材料，不进入审计/Git
└─ backup.md           # 应用前原始字节；事务结束后按策略清理
```

`transaction.json` 是规则变更恢复事实源，状态固定为：

```text
prepared -> applying -> validating -> succeeded
prepared -> expired | rejected
applying | validating -> rolling_back -> rolled_back | recovery_required
```

写入流程固定为：

1. 在事务目录保存候选并写入 `prepared`；文件权限限制为当前用户；
2. 使用共享规则验证器对候选执行内存校验，并通过“候选覆盖”模式运行完整结构校验，正式文件尚未变化；
3. 应用前再次检查全仓干净、revision、原哈希和令牌绑定；
4. 读取原始字节到 `backup.md`，在目标同目录写 UTF-8 无 BOM 临时文件，刷新文件后用 `os.replace` 原子替换；
5. 对正式文件再次运行完整结构校验；成功后写终态和审计；失败时用备份原子恢复并再次校验；
6. 服务启动时扫描非终态事务：若当前哈希仍等于候选哈希则恢复备份；若目标已被第三方再次修改，则绝不覆盖，标记 `recovery_required` 并在系统状态页提示人工处理。

临时文件必须与目标同目录。任何异常都不得删除唯一备份；成功事务可以清除候选与备份，只保留无正文的安全元数据。过期 `prepared` 草稿可按固定保留期清理，但不得清理 `applying`、`validating`、`rolling_back` 或 `recovery_required`。

## 6. 共享验证器与审计 v4

阶段 4A 先把现有规则预算、职责词、禁止词和绝对路径检查提取为共享 Python 规则验证器；`validate-structure.ps1` 与 Web 预览调用同一实现，避免两套规则漂移。验证器必须支持目标规则 ID 和服务端创建的候选文件，不能接受浏览器物理路径。

审计扩展为兼容 v1/v2/v3 的 schema v4，新增固定安全字段：

- `change_id`；
- `resource_type=rule`；
- `resource_id`，只允许静态规则 ID；
- `before_hash`、`after_hash`，只允许 64 位十六进制摘要；
- `rollback_status`，只允许固定枚举。

审计记录预览拒绝、应用开始、成功、回滚成功和需要人工恢复。审计不保存正文、diff、备份、物理路径、Git status 原文或底层异常。Web 审计查询必须显式投影新字段，并保持旧版本记录可读。

阶段 4A 新增内部动作 `rule.user.update`，风险级别扩展为 `source_write`，副作用固定为 `write:control_rule:user`。该动作只接受服务端生成的 `change_id`，由内部规则事务执行器处理，不启动 Shell，也不接受正文、路径或命令参数。任务事件只报告“校验、应用、复核、回滚”等语义进度。

## 7. 威胁与失败矩阵

必须覆盖以下负向场景：

| 场景 | 必须结果 |
|---|---|
| 未知或只读 `rule_id` 尝试写入 | 404 或能力拒绝，不回显路径 |
| 绝对路径、穿越片段或符号链接替换目标 | 拒绝，不能逃逸静态目标 |
| 非 JSON、缺少自定义头、跨 Origin 或伪造 Host | 拒绝且无草稿落盘 |
| 基线哈希、revision、diff 或令牌不匹配 | 409/确认失败，不写正式文件 |
| 两个客户端同时应用同一预览 | 最多一个成功，另一个稳定冲突 |
| 控制仓存在任意未提交或未合并状态 | 拒绝预览和应用 |
| 候选缺少职责词、含禁止词/绝对路径、超预算或含 U+FFFD | 预览失败，不写正式文件 |
| 临时文件写入、`os.replace` 或正式复核失败 | 原文件保持或恢复，任务和审计终态一致 |
| 应用后服务崩溃 | 启动恢复按哈希回滚；第三方再修改时不覆盖 |
| 审计写入失败 | 写入默认失败关闭；不得出现已修改但无审计关联的成功响应 |
| 页面刷新、重复提交、过期草稿 | 不重复写入，状态可恢复且令牌不可复用 |
| 中文、CRLF、UTF-8 无 BOM 和长行边界 | 规范化结果可预测，无乱码或 U+FFFD |

规则写入与普通审计不同：审计关联失败不能 fail-open。开始应用前必须成功写入审计开始事实；完成或回滚事件暂时写入失败时，事务保持非终态并阻止新的规则写入，直到可补写或明确进入人工恢复状态。

## 8. 开发波次与任务分发

实际开发仍由主会话负责集成、风险决策和最终审查，具体实现任务分发给 Luna 模型、推理强度高的子会话。波次之间严格串行；同一波次只并行分发文件边界不重叠的任务。静态注册表、审计 schema、应用入口和最终集成由主会话统一审查，子会话不得自行扩大可写规则、动作或路径范围。

建议分工如下：

| 波次 | 可并行任务包 | 主会话审查重点 |
|---|---|---|
| 0 | 共享规则验证器；审计 v4/安全投影；事务与 API 类型契约 | 单一验证事实源、旧审计兼容、路径不可注入 |
| 1 | 后端规则读/预览服务；前端规则中心；API/同源负向测试 | 预览零副作用、完整 diff、只读能力不误报 |
| 2 | 原子写入与恢复；任务/审计关联；前端确认和失败状态 | 锁与令牌次序、失败恢复、正文不进入事实源 |
| 3 | Windows 故障注入；浏览器流程；文档与发布核对 | 真实进程/文件边界、最终哈希、双仓无越界 |

每个子任务必须返回修改文件、关键决定、测试结果和未覆盖风险；主会话在合并审查后统一运行该波次的全量门禁，再决定是否进入下一波。

### 波次 0：契约与共享验证基础

- 冻结静态规则注册表、规则 ID、读写能力和内容预算；
- 提取共享规则验证器，并让结构脚本复用；
- 定义规则读模型、变更事务 schema、风险枚举和审计 v4；
- 建立临时 workspace 的单元、契约和损坏恢复夹具。

验收：现有结构校验行为不退化；候选覆盖校验不修改正式文件；v1-v3 审计继续可读。

### 波次 1：只读规则中心与预览

- 实现规则列表/详情和只读安全投影；
- 实现候选规范化、完整 diff、草稿事务和确认令牌绑定；
- 实现规则中心三栏页面，四项规则均可审阅，只有 `user` 可进入编辑；
- 覆盖深层路由、刷新恢复、超预算和跨站请求负向测试。

验收：没有 apply 路由时仍形成完整的只读审阅与预览闭环；预览不会改变 Git、规则文件或审计事实源。

### 波次 2：原子应用、回滚与任务关联

- 实现 `rule.user.update` 内部动作和规则事务执行器；
- 实现 apply API、全仓锁、原子替换、正式复核和自动回滚；
- 扩展任务事件、系统恢复提示和审计查询；
- 覆盖并发消费、进程崩溃、文件占用、审计失败与第三方修改。

验收：所有失败注入下原文件保持或可恢复；每次应用都有任务、变更事务和审计三方关联；不产生 Git commit/push。

### 波次 3：真实 Windows 与浏览器终验

- 在临时复制的控制仓执行成功、校验拒绝、并发冲突、回滚和崩溃恢复；
- 核对真实控制仓仅在用户明确终验且已备份时执行一次等价内容往返，不改变最终哈希；
- 浏览器覆盖规则审阅、差异确认、失败提示、任务跳转和刷新恢复；
- 完成结构、MCP、后端、前端、构建、安全扫描和 UTF-8 回归。

验收：阶段 4A 第一小版本满足本文件全部门槛后，才能考虑扩大可写规则或启动 4B。

## 9. 阶段 4B 阻塞条件

安装与修复不是 4A 的顺带任务。开始 4B 前必须另行冻结：

- Codex 与 Claude Code 的目标文件白名单、受管区块、备份和恢复规则；
- 用户级环境变量修改的预览、旧值保存和回滚；
- 安装动作拆分，不允许一键脚本同时隐式运行测试、写配置、重建索引和 probe；
- 每个 Agent 独立动作 ID、参数枚举、超时、重启提示和真实 handler 回归；
- 已有用户配置冲突、损坏 JSON/TOML、文件占用、权限失败和部分成功的事务语义；
- macOS 设备未就位前所有 4B 动作继续只支持 Windows。

在这些条件形成独立前置契约前，阶段 4B 不得分发实现任务。
